# 角色化语义框架：设计依据与贡献边界

本库解决中文多文档命题形式化中的一个具体问题：数值和事件陈述进入逻辑前，
需要确定它们在命题中扮演什么角色，以及属于哪个主体、时间、场景和行动意图。
例如，“实际单次量”和“推荐单次量”都是数值，但不能互换；“建议完成检查”
和“检查已经完成”涉及同一种操作，却提供不同的证据。

本实现采用两层表示：`core.json` 定义可组合的计算关系；`frames.json` 定义
语义角色及其绑定要求，再展开到同一组计算关系。记录选择和求解沿用现有流程。
以下原则是设计依据，不对应额外的独立系统。

## P1：用框架与角色描述含义，并让角色影响绑定

FrameNet 将词义放在框架中描述，框架元素具有相对于该框架的语义角色，并用
标注例句说明角色如何在文本中实现。它为“先确定关系含义，再识别参与者”提供
语言学依据。[Baker、Fillmore 与 Lowe，The Berkeley FrameNet Project，ACL/COLING 1998](https://aclanthology.org/P98-1013/)

本项目采用这一思想，把“单次量符合推荐”表示为 `observed` 与 `reference`
两个角色。角色同时规定所需数量含义及来源语境，而不是只写底层 `Number`。
例如，实际单次量来自所指实际状态，参照上下界来自原句指定的医嘱或推荐方案；角色要求
参与引用候选选择，随后才展开 `lower ≤ value ≤ upper`。

这是本项目的建模选择：框架角色连接到固定来源记录，同一角色的多个字段通过
同一引用共同选择。它不是直接移植 FrameNet 的英语词表，也不声称 FrameNet
已经提供本项目的医疗计算公式或中文多文档绑定算法。

语义槽与来源字段名通过引用的 `slots` 显式对应，例如剂量槽可读取 `dose_mg`
或 `dose_tablets`。参数角色不因字段拼写变化而变化；类型及单位检查作用于映射
后的字段。不同药品的计量口径可以并存，同一个比较仍要求口径相容。

## P2：显式保留医疗语境，区分指称与待判属性

SNOMED CT 的显式语境模型分别描述相关临床内容、主体关系、时间，以及发现
或操作的状态。这支持将“谁的、何时的、存在与否、执行到哪一步”作为意义的
组成部分。[SNOMED CT：Situation with Explicit Context Defining Attributes](https://docs.snomed.org/snomed-ct-specifications/snomed-ct-editorial-guide/readme/authoring/domain-specific-modeling/situation-with-explicit-context/situation-with-explicit-context-defining-attributes)

FHIR 的工作流模式进一步区分活动定义、请求与事件：请求表达建议、计划或
医嘱，事件描述活动或观察的进行与完成；请求存在不保证其被执行。我们据此
保留意图与实际状态的区别。[FHIR R5：Workflow Resource Patterns](https://hl7.org/fhir/R5/workflow.html)

本项目把这些区别落实为两个位置：

| 位置 | 内容 | 例子 |
|---|---|---|
| 引用定位与角色要求 | 命题已指明的主体、对象、时间、场景、来源及陈述角色 | “本次检查”“文档 B 的推荐方案” |
| 查询表达式 | 仍需判断的属性或关系 | “已完成”“对象相同”“剂量符合” |

因此，问“检查是否完成”时不能用 `completed = true` 筛选记录；问“实际药品与
推荐药品是否相同”时不能先要求二者身份相同才允许比较。这种分离是本项目针对
命题判定的设计取舍，不是声称 FHIR 或 SNOMED 规定了我们的查询接口。

跨语境比较也是显式关系。实际值和推荐值各自保留来源；推荐上下界共享同一
方案。除非原命题明确要求，不自动加入药品身份、患者适用性或其他合规条件。
通用建议也不因缺少具体患者身份而被补写为当前患者事实。模拟场景的实际值
保持所属场景，不继承历史真实患者数值。

## P3：通过组合展开定义；未知由证据语义决定

CQL 提供有类型的临床表达式、带单位的数量，以及可组合的运算与函数。这是
将人可读定义与可执行逻辑连接起来的医疗领域参考。[CQL：Developer's Guide，Types](https://cql.hl7.org/03-developersguide.html#types)

本项目复用少量基本运算：单次量与日频次相乘得到名义日总量，区间判断表达
数值符合，AND/OR/NOT 保留命题结构。单次量符合、两个维度分别符合和日总量
符合使用不同框架，避免把相同乘积误当作两个维度分别相同。单位与数量含义
必须在来源绑定时相容；这不意味着本库已实现 CQL 的全部类型或单位换算系统。

未知继续采用现有求解器的证据蕴涵语义。设固定来源事实为 `E`，展开后的
查询为 `Q`；在 `E` 可满足且求解完成的情况下：

| 检查结果 | 标签 |
|---|---|
| `E ∧ ¬Q` 不可满足 | `supported` |
| `E ∧ Q` 不可满足 | `refuted` |
| 两者都可满足 | `not_determined` |

字段 `null` 或缺省表示该字段没有提供值约束，不改变字段类型，也不自动成为
否定。实际记录的完成状态未知时，计划记录中的完成目标不能填充它。候选记录
字段未知仍可被选中；引用无法定位则是绑定未解决，不能伪装成已定位属性未知。

CQL 对缺失值通常采用 `null` 传播，并为逻辑等运算单独规定行为。当前 Z3
模型检查与这种逐运算语义并不相同，因此本库只借鉴其类型与组合原则，不声称
CQL 语义兼容。[CQL：Language Semantics，Execution Model](https://cql.hl7.org/05-languagesemantics.html#execution-model)

## P4：用能力问题与最小语义对照决定库的范围

TOVE 本体设计方法从应用情境出发，用系统必须回答的能力问题确定所需术语、
语义和约束。我们用它约束库的增长：只有出现无法表达或无法区分的命题含义时，
才增加定义或细化角色。[Grüninger 与 Fox 的 TOVE 方法，作者实验室说明](https://eil.mie.utoronto.ca/theory/enterprise-modelling/entmethod/)

本项目把能力问题落实为可执行的最小对照：

| 能力问题 | 仅改变的因素 | 必须观察的区别 |
|---|---|---|
| 当前还是历史的单次量符合？ | 查询时间 | 选择不同时间的实际记录 |
| 单次量符合还是日总量符合？ | 比较维度 | 同一批值可产生不同判定 |
| 推荐检查还是实际完成检查？ | 陈述角色 | 意图不能填充实际完成状态 |
| 未完成还是未记录？ | 事实的确定性 | `refuted` 与 `not_determined` 不混淆 |
| 当前用药与指定药品相同吗？ | 对象身份 | 候选仍保留不相同的实际对象，结果由比较得到 |

同义改写、文档拆分和来源顺序改变属于保持意义的对照；主体、时间、意图和
否定作用域改变属于可能改变意义的对照。测试应分别覆盖两类行为。人工对照
用于检查表示和编译性质，不等同于真实模型能够正确抽取这些结构。

## P5：规范输出与实际事实分开，条件规则保持方向

Input/Output Logic 将条件规范作为有方向的输入/输出对处理，区别于事实层的
材料蕴涵；条件规范通常不适合逆否推理。这为“禁止某行为”与“该行为没有发生”
分离提供依据。[Makinson 与 van der Torre，Input/Output Logics，JPL 2000](https://icr.uni.lu/leonvandertorre/papers/jpl00.pdf)

本库只借用这种分离，不实现整套 I/O 闭包、规范优先级或冲突消解。实际适配是
一条有来源的规范实例 `(condition, modality, action)`；condition 读取指定主体、
时间和场景的实际记录。查询“这条禁止规范是否适用”展开为
`modality = prohibition AND condition`。这是关于所指规范适用性的命题，
不是把其动作输出加入实际事实，也不是任意规范集合的义务可推导性算法。

实现保留原先的 rules 容器，事实关系使用 expr，规范关系使用 when/modality/action。
lower 将规范与事实前提分开；模型用 directive_applies(rule_id, modality) 调用。
原始规则及来源保留在 record_graph.directives；实际事件仍在 records 中。
这一步只展开显式规范，不分析原文纠错，也不修复模型仍用旧 expr 写出的错误规则。

最小能力对照是：条件成立且行为已经执行时，禁令适用与实际执行可同时为真，
事实层不矛盾；条件未知时不因原文提到该条件而把它断言为真；条件不成立时，
只能得到所指禁令不适用，不能得到全局许可。action 是该来源规范的行为指称，
由生成阶段选对规则与动作；当前编译器不验证这项自然语言对应关系。

## P6：根据语义保真义务分类，局部修复并接收执行反馈

2026-11-14：分类的可读、可执行定义保存在
[error_taxonomy.json](error_taxonomy.json)，当前版本1.1。运行时提示与分析使用同一份定义。
这是本项目依据既有理论与标准组织的框架，不是某个标准已经规定的完整错误分类表。
FormalRx启发了“类别、位置与修复一起输出”的方式；本实现使用现有DeepSeek模型，
未使用FormalRx权重、训练数据或训练过程，不称为FormalRx模型复现。
[FormalRx，ICML 2026](https://proceedings.mlr.press/v306/wang26cg.html)

| 类别 | 被违反的要求 | 理论依据 | 判定边界 |
|---|---|---|---|
| 表示合法性 `representation_validity` | 结构、参数签名、类型、单位和引用必须符合语言要求 | 类型系统；[HL7 CQL类型推导](https://cql.hl7.org/03-developersguide.html#type-inference) | 字段值未知本身合法；类型声明、访问路径或槽映射缺失属于表示问题 |
| 概念与角色保真 `concept_role_fidelity` | 关系含义、参数角色对应原命题 | P1的框架语义／FrameNet | 日总量与单次量是不同关系；关系正确但绑定到不同时间的记录归语境问题 |
| 语境保真 `context_fidelity` | 主体、时间、场景、意图与执行状态及记录关联保持 | P2的SNOMED CT显式语境、FHIR请求／事件分离 | 实际与推荐可以合法比较；丢失各自语境或拼接不同方案才是问题 |
| 逻辑与知识状态保真 `logic_knowledge_fidelity` | 条件、否定作用域、连接词和证据确定性保持 | 组合逻辑语义、模型论蕴涵、[开放世界假设](https://www.w3.org/TR/owl2-primer/)；P5的规范／事实分离 | 未记录不等于否定，查询不能成为前提；unknown不是待修复错误 |

分类依据是违反的要求，不能把Python异常名直接当作语义类别。例如缺少dose、
frequency和completed映射是同类表示问题。`frame_reference_context_conflict`
可能来自模型错绑，也可能来自库接口限制；诊断需要对照原文，不能把报错当成
语义错误的金标。后一种情况可以用已有原子表达式保留原意，不能谎改record的类别。

一个独立问题记录一个主要类别；有多个独立原因则分别记录。四个维度不被宣称为
天然互斥或穷尽。概念、语境和逻辑可相互影响，主要类别说明优先要修正的语义决策。
出现模糊案例时记录其理由，而不是为每个具体报错新增标签。

来源版本、模拟场景、共同引用绑定是本项目对上述理论的操作化扩展。一个可能有
场景意义的细类是“跨记录组合错误”：分别有证据的字段被组合成原文中不存在的
方案。暂作为语境类实例，只有在多个来源／模型中反复出现、能够一致标注、且有
对应机制的实证效果时，才考虑作为论文中的独立失效模式。

实现位于[frame_repair.py](../methods/frame_repair.py)，使用新实验臂
`frame_direct_repair`或`frame_direct_guard_repair`，原实验臂保留作对照：

1. 对原图调用现有编译器和求解器，保存原始图、执行结果及编译错误。
2. 同一个模型先诊断，仅在发现具体错误时给出局部修改，两步在一次调用内完成。
   输入为公开任务、已读取原文、图、四类定义、语义目录和程序诊断；可执行图还提供
   程序实际选中的记录及字段绑定。不传标准答案、评分目标或求解得到的标签。
3. 每个问题输出category、reason、evidence和edits。edit包含collection、id、path、value：
   records/references/rules按id定位，queries按item_id、properties按name定位；模型统一
   将该标识填入edit.id，由程序找到对象。path只描述该对象内部的字段，不再用数组
   位置指代记录或命题。正确图允许issues=[]，补字段可添加末级键；path=[]表示
   新增或整体替换指定ID的对象，value=null时删除该对象。
   若模型输出含edits=[]的条目，执行时不产生修改，不因该条目拒绝其他修改。
   因此诊断条目数与实际修改数须区分，不能把所有条目计为确认发现的错误。
4. 应用修改后重新走同一编译器和求解器。成功即进入实际保存／提交路径，不再
   发起语义复核。任务命题ID和文本不允许被改写；最终标签只能来自求解器。
5. 若修改应用、编译、引用解析或形式化执行仍报错，把当前图和具体报错追加到
   同一模型会话，让模型继续局部修复。保留前一轮修改，便于定位此次错误；
   修改无法应用时则保留尚未改动的图并反馈应用错误。所有轮次共用原Context预算。

每张图先做一次诊断；后续调用仅由真实执行错误触发，成功即停止。
not_determined是成功执行得到的合法标签，不触发反馈修复。没有训练、投票、
温度搜索、额外轮数上限或失败回退。若原版Guard要求补读，原agent继续读取并
生成新图；读取、首轮诊断、反馈修复、重放和Guard补读共用每阶段40次模型请求上限，
耗尽仍失败则按失败计分，绝不重置预算。网络错误沿用现有传输失败处理。
每轮保存repair_round_NNN.json，记录报错、诊断、修改后的图、求解结果及调用数。
同一接口版本可严格重放单次修复回包，仅新增失败后的反馈调用来做对照。
按ID定位改变了修复接口格式，因此该版本重跑保留旧读取与首次图，重新生成修复回包。

模型生成的类别和理由是诊断建议，不是经过证明的语义金标。编译成功仅证明当前
表示可执行。合成集的脚本化模型测试用于验证接口、预算和流程，不证明DeepSeek
具备这些诊断能力；真实小批量另行报告纠错收益、误改和成本。

### P6补充：未知参数、未知命题与分类对应的修复范围

`core.json.binding_semantics`明确区分两种未知：关系已经确定但缺少参数时，
保留关系并读取有类型的null字段；缺少某状态的判定依据时，读取未赋值的Bool，
不凭空增加阈值或充分条件。依据是组合语义与开放世界假设：缺少约束不蕴涵真假，
但整条组合命题仍可能被其他约束确定，例如false AND P为false。读取查询字段
不会断言该字段；同一性x=x仍是恒真式，求解器的等号语义不变。

纠错输入增加上述绑定语义，以及程序从图中整理的`missing_source_values`
（记录ID、字段、声明类型）。该表只表示缺少直接赋值；来源规则仍可能约束字段，
所以程序不依据该表直接赋not_determined。首次读取／生成接口与回包保持原样。

四类定义新增`repair_scope`。对表示合法性类，修改应用器保留已有合法操作的
关系结构、组合条件和比较字面量，允许修复引用地址、类型声明、槽映射及不合法的
操作签名。越界修改作为应用错误进入已有反馈循环，不增加独立核对器或模型调用。
这是本项目对表示修复范围的约束，不是CQL既定规则或语义等价证明：地址换错、
来源事实抽错，以及模型错误地选择概念／逻辑类后删除条件，仍可能逃过结构检查。
语义类别可以修改确有错误的关系；是否存在原文冲突仍由同一模型判断。

2026-11-14同8例重新调用修复流程，60项相关本地测试通过。相较上一版ID＋反馈：
提交8/8→7/8，正确命题31/38→28/38，整包全对4/8、E4/8、J3/8均不变。

但同包C1删掉实际剂量比较，refuted被误改成supported，抵消了这条收益。

KeyError('id')，全阶段4次原前缀＋36次修复达到40次，整包未提交，损失原有3条正确。
其最终图未改变；不能将未提交解释为C2已被修成未知。新增结构范围检查在本轮
没有实际触发，因而不能从这轮得分宣称它产生收益。

## P7：任务规格拥有查询，纠错只完成带类型的绑定

2026-11-14新增实验臂`frame_direct_guard_spec_repair`，实现于
[frame_spec_repair.py](../methods/frame_spec_repair.py)。原ID纠错实验臂仍可作为对照。
本次改变的是纠错语言可表达的修改空间，不增加一个独立的语义核对器。

理论依据与本项目适配：

- 前提与目标分离：分别建立来源约束F和查询Q，F不支持Q本身不是形式化错误。
  [LINC，EMNLP 2023](https://aclanthology.org/2023.emnlp-main.313/)采用分别翻译前提和结论、交给证明器的流程。
  本项目把任务文字与来源图分开，并取消绑定器写入查询和事实值的操作。
- 程序草图与受规格约束的候选空间：
  [SKETCH，ASPLOS 2006](https://people.csail.mit.edu/asolar/papers/Solar-LezamaTBSS06.pdf)用带空位的程序表达结构，
  [SyGuS，FMCAD 2013](https://www.microsoft.com/en-us/research/wp-content/uploads/2013/05/fmcad13.pdf)用语法和逻辑规格约束实现。
  本项目让规格拥有条件、常量和运算，只给后续绑定开放有类型的槽。
- 类型驱动补全可参考[Synquid，PLDI 2016](https://people.csail.mit.edu/polikarn/publications/pldi16.pdf)。
  当前实现只检查Bool/Int/Real/String和数值运算，并不实现该论文的精化类型合成、单位证明或完整SyGuS搜索。
  候选绑定仍由同一个DeepSeek模型生成，程序进行确定性实例化与类型检查。

执行流程：

1. 复用原agent实际读取与首次图。将原始图和执行结果留作对照。
2. 单独一次模型请求只接收claims、scenario_contract和通用关系库，生成roles与queries。
   该请求没有来源观测、原表达式、求解标签或评分目标。规格语法/类型错误回到同一会话；
   有效规格保存在当前Context，原Guard补读后复用，不再按新来源值重新解释题目。
3. 绑定器接收固定规格、原图的properties/records/rules及已读取observations。
   输出bindings以角色ID索引，每个角色指定一条record_id并映射字段；角色内共享记录。
   types按属性name修改类型声明，evidence_ids按命题ID更新引用；类别只说明问题，不授予额外修改权限。
4. String槽绑定字段或null；Bool槽还允许来源字段的NOT极性转换；数值槽允许同一记录字段的加减乘除。
   绑定不能填常量真值、等式、AND/OR或任意查询表达式。未取得的字段用类型化未知量，不写成事实。
   程序从规格展开原关系库并代入绑定，原来源值及rules保持原样；没有自由替换查询的操作。
5. 原求解器给出标签并沿原保存／提交路径执行。绑定、字段或类型错误进入同一反馈循环。
   规格生成、语法反馈、绑定、执行反馈、原生读取与Guard补读共用40次物理请求预算；失败不重置预算。

该实现保证已接受的规格在绑定期间不被改写，不保证规格忠实于自然语言。
来源值不被改写也不代表原agent抽取正确或足够完整。尤其是原图可能把属性编码成Bool，
新规格却要求String或集合；当前补全语言未必能表达合法转换，不能据此断定来源缺少信息。

81项相关本地测试通过，覆盖只读规格、禁止以类别绕过写入权限、未知区间及Bool、
共享记录、ID定位、来源值不变、任务ID/文字归属、错误反馈、Guard复用规格及40次总预算。
本地测试使用脚本模型，检查程序契约，不证明实际模型能稳定生成规格。

相同8例在线实验`runs/frame_spec_repair_pilot_20261114`：相较上一版未知语义纠错，
提交7/8→5/8、正确命题28/38→18/38、E4/8→3/8、J3/8→2/8；较早ID版为31/38。
S000269-C2和S000011-C6均得到正确not_determined，S000011-C1保留确认剂量比较并恢复refuted。
两个原始全对对照仍各4/4。成功提交的5例均核验规格不变、实例化一致、原来源值/rules未改。

但三个案例在规格阶段耗尽40次：S000176/S000547各36次输出all_of多位置参数，
而定义要求单个列表参数；S000636的36次规格输出均为非法JSON。另有规格语义错误：

S000011-C6虽然标签正确，也增加了“数据已考虑”等不准确的Bool，不能认定完整形式化正确。

## 本实现可以验证什么

本地语义测试应检查以下四项，而非只检查输出 JSON 的形状：

1. **角色约束有效**：相同记录和匹配分数下，加入角色语境可排除明确不兼容的
   绑定；单次量、日总量、执行状态各读取对应角色。
2. **来源固定**：改变查询、绑定或外层否定，不改写来源事实；查询不成为前提。
3. **共同绑定有效**：同一方案的边界、剂量和频次共同读取，跨方案不拼接。
4. **待判内容不参与选择**：在指称保持不变时，更改查询的真假条件不按答案
   重排候选；字段缺省不会使匹配记录自动消失。

一个有限的编译正确性目标是：给定正确的来源抽取、角色绑定以及满足定义适用
前提的参数，框架展开与其定义具有相同含义。模板展开可逐项验证；这一目标不
证明模型理解中文正确，也不证明候选评分正确。

## 贡献如何表述

框架语义、显式医疗语境、类型与逻辑组合、能力问题都是已有思想。当前可明确
描述的工作是：将这些思想落实为中文多文档命题的可执行框架库，让角色要求
参与来源绑定，表达共同绑定和跨语境比较，并区分指称条件与待判属性。

“降低形式化错误”与“提升 benchmark 表现”是待验证的研究假设。验证应比较
自由表达式、固定框架但关闭角色语境约束、完整角色语境约束，控制来源记录、
模型预算及评分方式，并分别记录框架选错、角色绑错和逻辑执行错误。开发时
反复看过的失败案例用于开发；未参与设计的来源簇用于检验泛化。单元测试通过
只说明所测表示与执行行为符合定义，不构成端到端性能提升证据。

这里记录的标准是设计参考，不要求引入完整 SNOMED 术语库、FHIR 服务或 CQL
执行环境。临床数值与患者事实仍来自本轮公开证据；框架库只保存关系语义。
